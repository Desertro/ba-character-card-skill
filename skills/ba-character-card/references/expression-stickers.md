# 立绘表情、情绪分类与聊天接入

## 从现有项目继续

先读素材清单、构建脚本、角色身份绑定和当前图集，逐张打开预览确认表情。不要为了补分类重抓全套素材，也不要把可见红晕自动归为恋爱、成人状态或固定关系。标签服务于聊天语义，不等于官方命名或人设事实。

微笑带泪可能是感动、感谢、释然或喜极而泣，不能只因嘴角上扬就标为得意／兴奋；区分无泪开心和痛哭。分类修正优先保留原表情 ID、路径与原图，只改 label／tags，让旧聊天引用仍可解析。新增派生用新 ID；从模型候选清单、历史表情说明和素材库检查新标签确实生效，不能只改图片文件名。

## 来源与编辑选择

优先复用用户指定素材或项目缓存；需要新增原图时查询可核对的原始素材页面／API，记录角色、服装、原始序号、原图／详情页 URL、取得日期、尺寸、SHA256、裁切框和产物哈希。图鉴缩略图或网页截图不能冒充原始透明素材；不同服装单独标注，不宣称全服装覆盖。

裁切按透明非零边界人工核对脸部、头发、光环和肩部位置，避免用所有角色同一坐标。带 Alpha 的立绘可缩放为 512×512 透明 WebP，并根据宿主显示需求添加细描边。具体尺寸与格式服从现有 App 约定。

脸红等小改动可在原眼睛、嘴型和轮廓不变的前提下局部叠色；人工确认腮红位置、边缘与强度。用新的 ID、`variantOf` 和参数区分本地派生／官方差分／AI 编辑，保留来源和授权说明。需要重新绘制眼神、姿态等超出局部叠色的视觉变化时，使用实际可用的图像编辑能力，不把简单腮红叠层说成新画的表情。

## 参数化离线构建

依赖 Python 3.10+、Pillow。已验证示例使用 Pillow 11.3.0。原图由具体项目提供，技能仓库不附游戏立绘或第三方卡包。

```text
python scripts/build_expression_stickers.py --config assets/momotalk-expression-recipe.json --sources PROJECT/branding/expression-sources --out OUTPUT_NEW_DIRECTORY
```

配方 `assets/momotalk-expression-recipe.json` 记录 2026-11-10 MomoTalk 项目的爱丽丝／诺亚／莉音默认服装实例：30 张原始裁切和 6 张局部脸红派生。它是固定历史实例，可用于对应来源缓存；换素材、服装或裁切必须核对并修改配方，不假定最新资源与它相同。实例包含公开来源 URL 和哈希，不自动下载。

配方顶层有 `packs`、`stickers`。角色包可提供 `key`、`name`、`aliases`、`sourceHashes`（用于项目角色身份识别，非图片哈希）。每张有唯一 `id`、`pack`、`label`、`tags`。

- 原始裁切：`source` 是相对 `--sources` 的文件路径，`sourceSha256` 用于确认原图；`crop` 为 `[left, top, right, bottom]`，坐标在原始 PNG；`url`／`descriptionUrl` 是来源。
- 局部派生：`variantOf` 指向配方中较早的同角色 ID；`cheekCenters` 为成品 512 图上的坐标；`overlay` 有 `radius`、`rgb`、`strength`。它沿用原图来源，并记录基底输出哈希与派生参数。
- 可选 `expectedOutputSha256` 固定产物；改配方后需先人工审核新图，再按实际结果更新预期，不能跳过哈希失败后声称原图相同。

输出目录须不存在。脚本先检查配方、所有路径和原图哈希，再在临时目录生成，成功后提交整个目录；失败不留下半成品、不覆盖旧包。产物是 `stickers/catalog.json`、`stickers/<pack>/*.webp`、`source-manifest.json`、`previews/` 和只含派生表情的 `stickers.zip`。预览缺少中文字体时用 `--font` 指定字体；未指定且不在 Windows 时预览用 ID 标注，避免把缺字方框误认为文本损坏。

## 接入聊天 App

角色绑定用稳定 ID、原卡哈希或明确别名；改显示名不应丢失本人表情，普通重名也不能无依据绑定。每轮只提供当前学生的 ID、中文 label 和 tags，模型输出可选 `sticker` ID；解析层白名单校验，拒绝未知、跨角色、路径和网址。没有需要时不发，纯表情是否允许按宿主协议验证。`reply:false` 不应偷偷发送表情。

表情 ID 保存到实际消息，重启、分支、重生成保持正确归属；给后续模型的历史描述使用“已发送表情：标签”，不把表情当真实经历，不反复上传立绘当用户图片。

`at`／`focus`／`read_air` 是参与维度，心情是独立维度；表情标签既不授予权限，也不重写关系。共用梗资料独立检索，按用户当前话题召回，限制数量／长度并保留来源，换题停止；不要让模型自己的梗触发无限召回。

对聊天 App 的操作先确认实际产品预期：单条重生成可在当前时间线替换，明确成功后是否移除旧后续；失败保留原记录。新分支必须是明确操作，不能把所有重生成都当成创建新分支。删除分支时明确确认、选择回退会话，保留独立子分支与共享图片；历史分支名字不要递归拼接后缀。这些是 App 集成检查项，不要求改写其他宿主既有的分支协议。

## 验证与交付

按任务范围验证：

- 资源：数量／唯一 ID、角色归属、尺寸／透明度、可解码、来源与输出哈希；分类修正后原图字节不变。
- 派生：逐张看图，验证 Alpha 不变、修改局限于声明区域；眼睛、头发和服装不误染。离线重建后关键产物相同。
- 请求／存储：本人候选清单、跨角色拒绝、文字与纯表情／静默、消息落盘、重启、历史标签和分支隔离。
- UI：实际收到并显示新 ID、素材库数量和新分类、切换学生、滚动到新图。MockWebServer 通过不等于真实模型会自然选图。
- 发布：APK 签名／CRC／assets 与当前代码一致；测试使用独立实例，不清用户主实例；覆盖安装前备份并核对包名、证书与用户文件。分别说明仅打包、已安装和真实接口实测。

源码包采用白名单，排除工具链、缓存、APK、聊天／备份、API 配置、签名密钥和临时探测脚本；包含必要源码、素材、参数、脚本、依赖说明与文件清单。解压到独立目录实际构建，逐文件核对哈希，清单不包含自己的哈希。技能仓库只放流程／脚本／小型配方，不上传用户项目成品或原作图片全集。测试有失败必须列出，不能沿用历史全量通过结论。
