# 批量角色库接入

当用户要求把多名学生集成到聊天 App 时使用。本参考只指导角色资料和接入，不要求改造已有平台的通用 UI。

## 身份与取材

- 固定每个默认衣装的游戏 ID、显示名、别名、学校与组织；不要用“同名档案中数值最小的 ID”推断默认服装，早期服装与支援位可能处在不同 ID 区间。NPC 没有学生档案时，使用已核实的显式说话人脚本和角色说明，保留来源缺口，不编造学生 ID。
- 扩展范围先对照本地已有快照。每名卡保留独立动机、口吻、同伴态度、兴趣、剧情阶段和新写示例；原作语音样本注明表/行/角色 ID。标题语音如“Blue Archive”不适合作为日常回复示例。
- 说明交付深度：档案加语音提炼的日常基础卡，不等于完整剧情记忆卡。不要把几十份基础卡声称为几十份成熟角色全集。已有深度卡应保留，不用批量模板覆盖。
- 同一衣装也可能有面罩/摘面罩、受伤等不同文件名；先查文件页与预览，不用受伤或其他服装差分悄悄替代正常日常形象。

## 稳定身份与升级

内置 ID、卡片源哈希、表情 pack、资料来源记录形成可追溯映射；展示名字与组织只是元数据。保存后的用户关系、名字、人设和世界书优先于内置默认值。升级只补缺少的卡，复用已有头像/聊天；改名或重启不新增重复学生，不重置关系，不将用户改名当成新角色。

分类信息可绑定稳定身份，导入卡可从其已知元数据恢复；无法确定的卡放入可见的自建/导入分组。旧角色和原图做一次封存基线，升级核对原卡、原表情和共享资料字节不变。后续重建某个表情包应合并该包，不能重写全目录并删除其他角色。

## 大量角色的操作入口

先检查现有产品的布局和使用方式。几十名角色通常需要独立角色库，学校→社团分组、姓名/别名/英文标识搜索、可取消的筛选及持久化常用标记；不宜把所有默认私聊一次堆进最近会话列表。群成员选择可复用同一目录，筛选变化不清掉已选项，显示已选数量并能逐人移除。表情浏览器也要支持搜索和滚动，原先三个按钮的一行布局扩到几十人会溢出。

每个角色的表情候选按身份白名单提供；同一群里的其他成员不获得她的表情 ID。共享梗按话题检索，不把整个多人库塞进每轮提示词。关系编辑的验证应查看下一次实际请求，不能只看编辑框内容。

## 具体核查

按本次改动选有区分力的检查：角色覆盖与唯一身份；JSON/PNG 卡数据一致；每包图像解码、透明度、标签及原图/输出哈希；新卡编辑、重启及升级保留；跨组织群聊请求中的本人关系与表情；搜索别名、空结果、筛选重置和跨筛选选人。核对实际 Release 的点击与正式包 assets，不以开发包界面测试代替正式构建检查。

Windows PowerShell 管道传中文给 Python 前显式设 `$OutputEncoding = [System.Text.UTF8Encoding]::new($false)`，或者将 UTF-8 脚本写入文件后执行；否则文件可能写进问号而两边断言也一起损坏。至少人工看一次实际界面中的中文提示和无障碍标签。

源码包包含应用构建所需素材、参数和来源清单；排除本机密钥、运行配置、聊天和备份。另一个 agent 接手时应能独立解压构建。可复用 skill 仓库只更新流程/脚本/小型配方，不随附整套游戏立绘或用户成品卡。全量测试的既有失败与新功能结果分别陈述。
